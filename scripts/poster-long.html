THE QUIET SIGNAL

改动落在哪些模块

出现在多少个 release 中（共 4,158 个有 diff 数据的发布）。

📄
docs 排第 3，1,625 次——比核心的 provider（1,487）还多。 文档不是事后补的：改行为就在同一个提交里改对应子系统文档。
这压住了 AI 最大的失败模式——过时的认知被反复当成依据。
THE PARADOX

「修遍每个兄弟位置」
和「55% 只碰 1~2 个模块」

它的规范里同时写着这两条。看起来矛盾，其实是配套的。

规范原文（docs/code-standards.md）实测
A fix reaches every sibling of the bug55.4% 只碰 1~2 个模块
One commit has one goal68.2% 只有 1 个提交
A change does only what its goal needs中位 6 个文件
A size budget is met, not raised10-23 后稳在 8 个上下
🔒
约束的是每次的改动量，同时禁止只修报告里那一个 case。
范围小 ≠ 修得窄。前者防混乱，后者防返工。
数据来源：magpie-releases 全部 4,162 个 release 的 published_at；对 4,158 个逐个调用 magpie 仓库 /compare/prev...tag 取得真实文件清单（4 个无共同祖先，已剔除）。
局限：时间关联不等于因果。10-07 规则升格 → 10-23 形态收敛这段，只能给出时间吻合，无法排除混杂因素（团队规模、产品阶段变化）。
